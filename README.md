# 🌌 Orbitto Service: Advanced Frontend Challenge

Искренне благодарю вас за время, уделенное изучению этого решения. Данный репозиторий демонстрирует не просто верстку макетов, а комплексный инженерный подход к построению масштабируемой и безопасной фронтенд-архитектуры.

---

## 🏗 Архитектурные столпы

Проект построен на трех фундаментальных решениях, которые подробно описаны в наших **Architecture Decision Records (ADR)**:

1.  **[BFF & Secure Auth (ADR-002)](docs/adr/002-secure-auth-strategy.md)**: Полный отказ от хранения токенов в среде доступной клиенту. Внедрен паттерн Backend-for-Frontend с использованием `HttpOnly` кук и пробросом IP клиента (`X-Forwarded-For`) для корректного Rate Limiting. Проксируем только запросы связанные с токенами, вместо проксирования всех запросов.
2.  **[Multi-Zones Scalability (ADR-001)](docs/adr/001-multi-zones-architecture.md)**: Использование Next.js Multi-Zones для разделения Auth-флоу и Dashboard на независимые приложения. Это позволяет командам работать автономно, сохраняя единый домен и общую дизайн-систему.
3.  **[FSD & Dependency Inversion (ADR-003)](docs/adr/003-fsd-and-dependency-inversion.md)**: Строгое следование Feature-Slicing Methodology с использованием паттерна `deps` для инверсии зависимостей. Это гарантирует отсутствие циклических импортов и легкое тестирование компонентов.

---

## 🛠 Технологический стек

- **Framework**: Next.js 15 (App Router + Pages Router в разных зонах)
- **Monorepo**: Nx + PNPM
- **Styling**: Tailwind CSS v4 (Native CSS-first approach)
- **State Management**: TanStack Query v5 (React Query)
- **Contract**: GraphQL (через типизированный SDK)
- **Architecture**: Feature-Slicing Methodology (FSD)

## 🚀 Как запустить

1.  **Установка зависимостей**:
    ```bash
    pnpm install
    ```
2.  **Настройка окружения**:
    Скопируйте `.env.example` в корень и приложения:
    ```bash

    ```

## Тестирование

В проекте реализовано три уровня тестирования для обеспечения надежности критических сценариев.

### 1. Unit-тесты (Логика и Схемы)

Проверка валидации данных и бизнес-логики в `libs/shared/api`.

**Что покрыто:**

- `auth.schema.spec.ts` — строгая валидация почты и проверка совпадения паролей при регистрации.

```bash
npx nx test api
# или запуск напрямую через vitest
npx vitest run -c libs/shared/api/vitest.config.ts
```

### 2. Integration-тесты (UI-компоненты)

Проверка взаимодействия React-компонентов с формами и валидацией (JSDOM).

**Что покрыто:**

- `sign-in.form.spec.tsx` — рендеринг формы входа, отработка состояний `loading`.
- `sign-up.form.spec.tsx` — проверка сабмита данных и отображения клиентских ошибок.
- `password-recovery.form.spec.tsx` — восстановление доступа по email.

```bash
npx nx test main
# или запуск конкретных тестов
npx vitest run -c apps/main/vitest.config.ts
```

### 3. E2E-тесты (Браузерные сценарии)

Полная проверка путей пользователя через Playwright.

**Что покрыто:**

- `auth.spec.ts` — сквозные сценарии авторизации, регистрации, проверка валидационных алертов в Chromium, WebKit и Firefox.

> **Примечание**: E2E тесты намеренно работают с реальным бекендом через BFF. Это гарантирует корректную проверку интеграции: установку HttpOnly кук, обработку реальных контрактов API и работу сети. В production-среде для CI/CD предполагается использование тестовой базы данных или эфемерного окружения для предотвращения мутации данных.

```bash
# Для запуска требуется работающий dev-сервер
npx nx e2e main-e2e
```

## 🧠 Инженерные аргументы и Trade-offs

### 1. Выбор фреймворка: Почему Next.js, а не SPA (React/Vue)?

Рассматривались классические SPA-решения на React/Vue из-за скорости разработки и простоты деплоя. Однако выбор пал на **Next.js** по следующим причинам:

- **Архитектурное разделение**: Макеты логично делятся на публичную часть (промо/BFF) и защищенный дашборд.
- **Multi-Zones**: Это "нативное" решение позволило объединить два независимых приложения под одним доменным пространством без необходимости сложной настройки Nginx. Это упрощает деплой и дает прозрачность конфигурации прямо в репозитории.
- **BFF (Backend-for-Frontend)**: Необходимость безопасного проксирования авторизации (HttpOnly куки) идеально реализуется через API-роуты Next.js.

### 2. Монорепозиторий: Nx vs Turborepo

Выбран **Nx** как более зрелое и гибкое решение "на вырост". Его возможности по строгому управлению графом зависимостей и генерации кода перевесили легковесность Turborepo в контексте структуры с несколькими зонами и разделяемыми библиотеками.

### 3. Интеграция с Backend и контракты

- **Выбор Backend**: Был выбран конкретный форк из-за наличия GraphQL-схемы и простоты внесения правок.
- **Изменения в Backend**: Я внес небольшие изменения в код бекенда, чтобы он мог принимать токены напрямую из кук. Это позволило сделать BFF максимально "глупым" и быстрым: он только проксирует логин/рефреш/логаут и выставляет куки клиенту, полностью полагаясь на валидацию и ошибки реального бекенда.
- **GraphQL Client**: Вместо тяжеловесного Apollo использован легковесный типизированный SDK, генерируемый по схеме. Кэшированием и состоянием запросов управляет **TanStack Query**, что дает больше гибкости и контроля.

### 4. Архитектура и качество кода

- **FSD & SOLID**: Строгое следование Feature-Slicing Methodology. Принципы SOLID выражены в инверсии зависимостей (DI) через типы и контекст, а также в использовании интерфейсов и фабрик имплементирующих эти интерфейсы для API-клиента и логгера.
- **Границы модулей**: Настроены линтеры для контроля внешних публичных API модулей (`index.ts`) и запрета глубоких импортов.
- **Инвестиции в Tooling**: Много времени было уделено настройке линтеров (fsd, сортировка импортов, Tailwind-классов) и автоматизации рутинных задач (генерация кода, автоформатирование). Эти решения отняли время сейчас, но существенно сэкономят его в будущем, предотвращая конфликты при слиянии и поддерживая единообразие кода.

### 5. Принятые компромиссы (Trade-offs)

- **Связанность доменов**: Решение с HttpOnly (sameSite: "strict") куками требует, чтобы фронтенд и бекенд находились на одном домене (или поддоменах) для корректной работы безопасности браузера.
- **Проксирование**: Мы проксируем только критичные для безопасности запросы (login/logout/refresh), остальные запросы идут к бекенду напрямую, что снижает нагрузку на BFF, но требует поддержки CORS на стороне бекенда.

## 🚀 Что дальше? (Production Roadmap)

Если бы это был реальный production-продукт коммерческого масштаба, следующими шагами стали бы:

### 1. Observability & Monitoring

- **Интеграция телеметрии:** Подключение Sentry для трекинга ошибок в реальном времени.
- **Performance Vitals:** Сбор Web Vitals на клиенте (`useReportWebVitals`) и замеры latency на уровне API-роутов BFF.

### 2. Security & Session Management

- **Token Rotation:** Переход к проактивному обновлению access-токенов по истечении TTL (на основе метаданных в куках) вместо реактивного перехвата `401 Unauthorized`.
- **Advanced Rate Limiting:** Усиление политик защиты от Brute Force атак на уровне IP-адресов.

### 3. CI/CD & Testing

- **Visual Regression:** Внедрение скриншотного тестирования (Playwright Visual Regression) для библиотек дизайн-системы.
- **Affected Builds:** Настройка CI-пайплайна для сборки и прогона тестов исключительно по задетым (affected) граф-модулям Nx.

### 4. DX & Type-Safety

- **Strict Env Validation:** Валидация переменных окружения через схемы (`zod-env`) на этапе старта dev-сервера.
